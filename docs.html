What VERIDIC is

VERIDIC is a voice-first agentic assistant for Windows. The distinction it draws is between talking about an action and performing one: when you ask it to open an application, move a file or check what is eating your CPU, a real function runs against the real machine and reports the real outcome.

The name is the design brief. Everything the assistant claims to have done is something a registered tool actually returned — if a launch failed, the failure is what you hear. There is no layer that smooths a failed operation into a confident-sounding summary.

The three pieces

  • The agent — a Python process (veridic_core/agent.py) holding the tool registry, memory, safety gates and the model session.
  • The interface — a Next.js application, also packaged as a Tauri desktop app, giving you fifteen screens over the same backend.
  • The transport — LiveKit WebRTC carrying audio in both directions between the browser and the agent.

On "local-first". VERIDIC runs on your machine and acts on your machine, and your files, memory and logs stay there. The default voice path, however, is not offline: speech recognition and synthesis are provided by Google Gemini Live over LiveKit, so audio leaves the device during a voice session. A fully-offline path (Whisper + Piper + Ollama) exists in the tree but is experimental and not yet fully wired. See Voice pipeline.

Architecture & boot chain

One command starts everything. veridic start runs a bootstrap that checks prerequisites, verifies your license, prepares both environments and launches the backend and frontend together.

1

veridic.bat → cli/bootstrap.py start

Entry point. Must be CRLF-encoded ASCII — cmd.exe mis-parses LF batch files and garbles the interpreter path.

2

Prerequisite checks, with auto-fix

Python 3.13, Node 20+, pnpm, MSVC C++ build tools and permissions. Missing pieces are installed rather than reported as an error.

3

License verification

verify_or_activate_license() checks the hardware-bound key, prompting for activation if none is present.

4

Environment setup

Creates the Python venv and installs requirements; runs pnpm install for the frontend. Both are idempotent, so repeat starts are fast.

5

Concurrent launch

pnpm dev starts Next.js on port 3000 and the Python agent side by side. An update check runs in the background and never blocks startup.

6

Session handshake

The UI calls POST /api/connection-details for a LiveKit participant token, joins the room, and the already-registered agent worker is dispatched into it. Voice begins.

Two modes, one file

agent.py reads voice.mode from configuration and branches at __main__. In cloud mode (the default, and the path that actually boots) it registers as a LiveKit Agents worker and Gemini Live native audio provides both directions of speech. In local mode it runs a native mic/speaker pipeline with no LiveKit at all. Same file, two entry points — not two competing implementations.

The voice pipeline

Voice is where most assistants feel slow, so it is worth being precise about who owns each stage.

ModeSpeech → textText → speechStatus
cloud
default		 Gemini Live native audio Gemini Live native audio Working. The voice.stt (Whisper) and voice.tts (Piper) config blocks are ignored on this path.
local Whisper (intended) Piper (intended) Incomplete. The voice loop is constructed with stt, tts and intent_router set to None.

Echo cancellation

An assistant that hears its own voice will interrupt itself indefinitely. In cloud mode this is handled by enabling LiveKit Background Voice Cancellation on the room input options, so the agent's own output is filtered out of the inbound stream before it reaches the model.

Model names go stale. Use the -latest native-audio alias rather than a dated preview tag. Dated previews are retired without notice and sessions then drop with 1008 Requested entity was not found — which looks like a network fault but is not one.

Latency tuning

Three knobs in the performance block matter most: launch_verify_ms (how long to wait after spawning an app before declaring success — lower is snappier, higher catches more crashes), mem0_timeout_seconds (hard ceiling on the cloud memory fetch at session start, default 0.5s), and async_logging (queues structured logs off the event loop so disk writes never stall audio).

Configuration

Everything non-secret lives in user_config.json. The blocks that matter:

llm — model routing

router_mode: "always_cloud" is the default and sends every request to Gemini. The local block configures an Ollama fallback (default qwen2.5:3b at http://localhost:11434) and is only consulted if you change router_mode away from always_cloud and an Ollama server is actually reachable. Leave it alone and the block is inert.

voice — the audio path

mode selects cloud or local. wake_word_enabled controls hands-free activation. The nested stt and tts blocks apply only to the local path — setting them in cloud mode does nothing.

extensions.features — feature flags

FlagDefaultEffect
extensions_enabledtrueMaster switch for the extension layer.

All optional; omit any value to take the default. Covers launch_verify_ms, mem0_timeout_seconds, local_memory_enabled and async_logging — see Latency tuning.

Deterministic execution

"Deterministic" here has a specific and limited meaning, and it is worth stating precisely so the claim is checkable.

The language model chooses which tool to call and with what arguments. That choice is a model output and is not deterministic. What is deterministic is everything downstream: once a tool name and arguments exist, execution is ordinary Python. The same arguments produce the same behaviour, the return value is the real result, and the result is what gets reported.

What this buys you in practice:

  • No invented paths. A file operation either resolves through path validation or fails. It cannot half-succeed against a plausible-looking directory that does not exist.
  • No invented success. launch_app waits and checks for an immediate crash. If the process died, you are told it died.
  • Auditable. Every invocation is structured-logged with its arguments and outcome, and security_audit reads that trail back.
  • Repeatable. An automation routine is a list of tool calls in a JSON file, not a prompt. It runs identically every time because no model sits in the loop.

The honest framing: VERIDIC does not stop the model hallucinating. It stops a hallucination from becoming a silent false success — the failure surfaces as a failure instead of a confident summary of something that never happened.

The tool registry

Every capability is registered as a named entry with a callable and a metadata block. The registry is a singleton built once at startup, and registration is fault-tolerant by design: each group is wrapped so that a missing optional dependency disables just that group. Playwright absent means no browser tools — not a failed boot. 

# How a tool is registered
registry.register("kill_process", kill_process_by_pid, {
    "description": "Kill a process by PID. Args: pid",
    "category": "system",
    "async": True,
    "requires_confirmation": True,
})

Metadata fields

FieldMeaning
descriptionWhat the model reads when deciding whether to call this tool. The single highest-leverage string in a tool definition.
categoryGrouping used for filtering and audit.
asyncWhether the callable is a coroutine.
requires_confirmationRoutes the call through the confirmation broker before it executes.
timeout_secondsPer-tool ceiling. Installers get 300s; most tools use the shorter default.

Guards applied at the boundary

  • Timeouts — every tool runs under a deadline, so one hung call cannot freeze the session.
  • Retries — transient failures retry on an explicit allowlist of exception types, not blindly.
  • Result stringification — tools returning rich ExecutionResult objects are wrapped so the model always receives clean text, with errors surfaced as Error: … rather than a mangled repr.
  • Safe subprocess — shell-outs go through a hardened wrapper that handles quoting, capture and termination.
  • Dry-run — destructive operations accept a dry_run flag that reports the plan instead of executing it. Installers default it to True.

Permissions & gating

Three escalating levels of restriction, applied per tool.

1 · Open

Reads and reversible actions run immediately: checking health, listing files, launching an app, querying memory. Requiring a confirmation for every read would train you to say yes reflexively, which is worse than not asking.

2 · Confirmation-gated

Marked requires_confirmation and routed through the confirmation broker, which suspends execution and surfaces the pending action — named, with its arguments — to the interface. Nothing runs until you approve. Covers process termination, folder deletion, file overwrites, package and driver installation, registry edits, virus scans, camera enablement, face registration, screen capture and conversation-history deletion.

3 · Token-gated

The sharpest tools additionally require a capability token that the model cannot mint: execute_script, configure_system_settings, and the mutating actions of manage_services. Confirmation alone is not sufficient — without a valid token the call is refused outright. This is the boundary that keeps a persuasive prompt from reaching arbitrary code execution.

Destructive-tool changes touch four places. If you add or rename a tool that can destroy data, its confirmation requirement has to be updated everywhere the permission set is declared. Updating the registry alone leaves a gap where the tool executes ungated.

Memory model

Memory operates on three timescales.

  • Session context — the active conversation window, managed to stay inside the model's context limit without dropping the parts that matter.
  • Local store — SQLite on disk, holding entity–attribute–value facts and relationships. Works offline, survives restarts, and is fully browsable and deletable from the Memory screen.
  • Cloud memory (Mem0) — optional cross-session recall, fetched at session start under a 0.5s timeout. If Mem0 is slow or down, the session starts anyway with local memory only.

Resuming a conversation

Resuming from the History screen passes the prior session through job metadata into the agent's chat context. This restores the agent's memory of the conversation, not merely the transcript you can see — so the resumed agent knows what was decided, not just what was said.

Forgetting

Deletion is a first-class operation at three granularities: forget_fact for one attribute, forget_entity for everything about a subject, and delete_conversation_history for the lot. The last is confirmation-gated and genuinely irreversible — there is no server-side copy to restore from.

Every screen in the app

The interface is a shell with a collapsible navigation rail, a command palette and a boot screen, running in the browser or as a packaged Tauri desktop application. Fifteen surfaces across three groups — and every navigation item is a real route. Items that are not finished render an honest "coming soon" page rather than a dead link.

Command palette

Keyboard-driven navigation and actions from anywhere in the shell. Where an action needs a live session it says so and takes you to the voice screen rather than silently failing.

The microphone is not published on the Chat screen. Opening a text conversation used to auto-publish the mic track; that is now gated behind an explicit flag on session start. Text chat means text chat.

Automation & workflows

A routine is an ordered list of tool calls stored in user_workflows.json, addressable by id or by a trigger phrase. Because it is data rather than a prompt, it executes identically every run — no model in the loop, no drift. 

// user_workflows.json — shape
{
  "id": "focus_mode",
  "name": "Focus Mode",
  "trigger": "start focus mode",
  "steps": [
    { "tool": "set_system_profile", "args": { "profile": "performance" } },
    { "tool": "launch_app",          "args": { "app_name": "Visual Studio Code" } },
    { "tool": "open_folder_by_name", "args": { "name": "projects" } }
  ]
}

Manage routines from the Automation screen or call them by voice. list_automations reports what exists — so when you ask what VERIDIC can do automatically, the answer comes from your actual configuration rather than from the model's imagination.

Proactive suggestions

The Sentinel engine watches for manual sequences you repeat and surfaces them through get_proactive_suggestions as automation candidates. Suggestions are advisory — nothing is created without you.

Plugin SDK

Drop a single .py file into veridic_core/plugins/ and its tools are auto-discovered at startup and become callable by voice. Discovery is anchored to an absolute path, so it works regardless of the process working directory. Requires extensions.features.plugin_system to be true. 

from extensions.plugins import JarvisPlugin, PluginManifest, jarvis_tool


class MyPlugin(JarvisPlugin):
    manifest = PluginManifest(
        name="my_plugin",
        version="1.0.0",
        author="you",
        description="What this plugin does",
        permissions=[],              # e.g. ["network"], ["filesystem"]
        entry_point="my_plugin.py",
        enabled=True,
    )

    async def on_load(self):    # optional lifecycle hooks
        pass

    async def on_unload(self):
        pass

    @jarvis_tool(
        name="my_tool",
        description="Clear, action-oriented description the LLM reads",
        permissions=[],
        requires_confirmation=False,   # True to gate irreversible actions
        timeout_seconds=5.0,
    )
    async def my_tool(self, some_arg: str = "default") -> str:
        # Type hints on args become the tool's JSON schema automatically.
        return f"did the thing with {some_arg}"

Restart VERIDIC and the tool is live.

Notes that save time

  • The description is what the model reads to decide whether to call your tool. Write it as an instruction, not a label.
  • Argument type hints become the JSON schema automatically — no separate schema to maintain.
  • Set requires_confirmation=True for anything irreversible. It costs one prompt and prevents an entire class of bad afternoon.
  • permissions declares intent up front and is surfaced on the Extensions screen, so a user can see what a plugin claims before enabling it.

REST API

veridic_core/api_server.py exposes a loopback HTTP API on port 8989. The Next.js app proxies /api/* to it for the endpoints it does not serve itself.

How it is protected

  • Presence, not values. GET /api/config returns booleans indicating which keys are configured. It never returns a key.
  • Origin allowlist. CORS is locked to localhost:3000 / 127.0.0.1:3000, extendable via VERIDIC_ALLOWED_ORIGINS. Unknown origins get no allow header at all.
  • Loopback plus custom header. Sensitive endpoints require the request to originate from loopback and carry X-Veridic-Local: 1. A hostile page cannot set that header cross-origin without triggering a preflight the allowlist rejects — which is what closes off CSRF and DNS-rebinding attacks against a local API.

Security model

Secrets

One source of truth: the gitignored root .env, overlaid onto the config at load. user_config.json carries placeholders only. Also gitignored: .veridic_lic, .license_secret, saved_files/ and brain/. If a key was ever committed in plaintext, rotate it — removing it from the working tree does not remove it from history.

Face ID

The login gate is a real control, not decoration:

  • Fails closed. If the backend is not ready, access is denied rather than waved through.
  • Majority match. At least 3 of 5 samples must match your registered centroid.
  • Lockout. After 5 failures (VERIDIC_FACE_MAX_ATTEMPTS) it locks for 300 seconds (VERIDIC_FACE_LOCKOUT_SECONDS). Both are environment-configurable.
  • No backdoor. There is intentionally no hardcoded bypass password.
  • Not a self-lockout trap. If no users are registered at all, the gate is skipped by design.

If it locks you out

  1. Set FACE_AUTH_ENABLED=false in veridic_core/.env, start up, re-run register_face.bat in good lighting, then re-enable the gate.
  2. Or wait out the five-minute lockout and retry with better lighting.

Do not lower the match threshold to stop lockouts. Re-registering under good lighting fixes the actual cause. Loosening the threshold turns a working control into security theatre while leaving you convinced you still have one.

Privacy defaults

  • Camera off until enable_camera is called explicitly; disabling is never gated.
  • Screen capture is confirmation-gated — a screenshot can contain anything on your display.
  • Files, logs and local memory never leave the machine.
  • Voice audio does leave the machine in the default cloud mode. Stated plainly because the alternative reading would be flattering and wrong.
  • Web scraping runs under data-governance rules rather than fetching any URL handed to it.

Licensing

Offline verification via HMAC-SHA256(HWID, master secret) — no license server, no phone-home. The master secret resolves in order: the VERIDIC_LICENSE_SECRET environment variable, then a gitignored .license_secret keyfile, then a legacy embedded fallback so previously-issued keys keep validating.

Issuing your own keys

Set VERIDIC_LICENSE_SECRET (or write .license_secret) before issuing real keys. Legacy-signed licenses stop validating at that point and must be reissued — which is the intended behaviour when you take over signing.

Build safety

build_release.py deletes developer-only files before packaging and runs a security gate that fails the build if the master-secret literal or a dev-only file is still present in cleartext. Run it standalone in CI with python build_release.py --check.

Known weaknesses, stated openly. A symmetric scheme must ship the secret in order to verify on the client, so it can never be truly hidden. There is also no expiry and no revocation. The recommended upgrade is Ed25519 signatures — sign {hwid, exp} with a private key you keep, ship only the public key — which removes the first weakness entirely and enables the other two. Not yet built.

Troubleshooting

Start with veridic doctor. It checks Python, Node, pnpm, VC++ build tools, audio devices, camera, API keys, Mem0 and Ollama in one pass. Logs rotate under %APPDATA%\Veridic\logs\veridic.log; set VERIDIC_DEBUG=1 for verbose output.

SymptomCause & fix
App appears dead on start Port 8989 conflict from a previous run. This self-heals — give it a moment before restarting. If it persists, check for an orphaned Python process.
Voice feels laggy Cloud-path VAD latency. Tune the voice.vad.* values in user_config.json; also check mem0_timeout_seconds is not set high.
It hears itself and interrupts Browser acoustic echo cancellation disabled at the capture site. AEC must be on where audio is captured — enabling it downstream does not help, and the symptom is echo plus added latency.
Mic opens during text chat Historic behaviour where the mic track auto-published on session start. Now gated behind an explicit flag — update if you are on an older build.
Session drops with 1008 Requested entity was not found A stale Gemini Live model name. Switch to the -latest native-audio alias instead of a dated preview tag.
"Permissions are: []" — every tool blocked A dual-import split created two copies of the safety module, so the registry populated one and the checker read the other. Fixed by anchoring the singleton to sys.modules and comparing permissions by value.
Bootstrap runs with a garbled path A root .bat file saved with LF endings or containing non-ASCII characters. Batch files must be CRLF and ASCII.
Face ID will not let you in Low light or appearance change. Recover with FACE_AUTH_ENABLED=false, re-register, re-enable — see Security model.
google_search missing Unregistered by default. Set VERIDIC_WEB_SEARCH_ENABLED=true and link a billing account to the Google Cloud project, or the API returns 403 on every call.

Known limitations

Documented deliberately. A reference that only lists strengths is a brochure, and you would find these out anyway — better here than at 2am.

  • Native-local mode is incomplete. veridic start-local targets fully-offline operation, but the voice loop is constructed without STT, TTS or an intent router. The voice.stt, voice.tts and llm.local config blocks apply only to this path and it does not yet consume them.
  • Windows only. Linux and macOS are roadmap items. The architecture is modular enough to make the port tractable, but it has not been done.
  • Default voice path is not private. Cloud mode sends audio to Gemini Live. Local processing of files and memory does not change that.
  • Licensing is symmetric. The verification secret ships with the client; no expiry, no revocation. See Licensing.
  • Google Custom Search is off. Requires a billing-linked Cloud project.
  • Optional dependencies change the toolset. Playwright, Windows Defender and the Minecraft bridge each gate their own tool group. Two installs can legitimately expose different tool counts.
  • Determinism has a boundary. Tool execution is deterministic; tool selection is a model decision. See Deterministic execution.
